# 游戏制作人工作与版本放行规范 v1.1
适用 Riftworks：原型、预制作、正式制作、测试和上线运营。制作人对目标玩家体验、范围、预算、依赖、交付及验收负责。项目由 AI 多 Agent 协作完成，默认产能高、迭代短、可并行，不能从传统人工项目的制作周期推导本项目延期。独立验收不能由同一个实施结论代替。

## 1. 里程碑先用可玩成果定义
每轮明确目标玩家、平台/设备、版本/commit、入口、主路径、完成条件、预期体验和本轮要证伪的假设。原型验证核心循环；垂直切片以代表性可玩内容验证目标质量、跨工种集成与后续内容生产方法，而非概念截图或功能数量。正式制作只扩大已经验证的核心模式。
所有里程碑状态按「未开始→制作中→集成中→验证中→独立验收通过」，可附「阻塞」原因。只有已测试冻结包才称验收完成；用户真实反馈、模拟、回调和原生录制分别记录。

## 2. 版本范围
优先级 P0=阻断主流程/数据正确/安全与平台基础，P1=本轮体验核心及关键可用性，P2=可独立推进的次要优化。不随意延期任何有价值的内容：优先通过独立工作区和 Agent 并行探索/制作，按玩家价值、设计证据、真实依赖与验收结果决定是否合入当前冻结版本。未合入当前版不等于停止制作，除非有可验证的失败反例、依赖未满足、需求尚未确认、安全/授权/预算限制或质量阻断；必须记录原因及下一步实际工作。分离实验与当前候选以便归因，避免把多个参数混调成无法追责的结果。范围争议由设计提出、反方挑战、制作人拍板，超过授权如成本、公开边界或根本方向由用户决定。

## 3. 角色、产能、依赖与日期
拆成可独立验收的交付物，逐项注明负责人、验收人、依赖、目标日期窗口及完成凭证。先冻结接口与可观测门禁，再并行设计、美术/互动、逻辑、音频；实现角色按文件所有权操作，集成者不回退其他角色。明确真实依赖和返修门禁；日期只用于协调、记录进展和真实外部限制，不是限制产能或规定等待的理由。采用 AI 分工并行、自动回归、可逆实验和持续集成。能提前完成即立即验收、合入或启动下一轮，不得把传统人力工期或没有数据的估时当作延期理由。
常用四角色闭环：对标与需求→反方挑战→实施（可多角色并行）→独立验收；制作人负责接口、范围、集成、外部条件和后续推进。版本和任务状态均要证据支撑。

## 4. 证据与风险
版本审查表：交付物｜优先级｜取舍理由｜负责人/依赖｜目标窗口｜状态｜可观察完成标准/证据｜验收人。
风险：触发信号｜影响（体验、产能、日期）｜建议处置｜负责人/决策人｜最晚决定时间。证据不足必须明确影响哪个放行条件，禁止用大量单元测试掩盖核心操作失败。每次范围变更留一条理由及回归路径。

## 5. 阶段性决策与发布
结论只选继续推进、补验证/修复、缩减范围/回退、公开测试放行，附冻结证据。一旦 P0 或 P1 阻断出现，停止公开切换，优先组织快速并行返工；仅在证据表明设计无效或真实依赖阻断且缩减不伤害核心体验时回退候选。不得为赶日期砍掉有价值内容；已确认资源、目标设备、可靠入口、关键错误恢复、回退包、真实商店内容与准确披露全部核验。外部玩家测试不是正式上线；公开之前应有内部可玩基础，不强等发布后本应取得的真人反馈。测试招募使用实际自有页、真实评论/数据，保持免费、无广告预算，禁止虚构玩家。
每版通过后开发分支提交和独立证据归档；发布验收阻断不应暂停可独立推进的开发、制作、实验及商店素材准备。二进制需依项目 LFS，不能提交悬空指针；完整工程归档及旧包可回退。正式结束时列三项近期行动、每项完成标准和关键风险，用户只在实质节点接收报告。
