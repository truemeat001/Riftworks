# P09 整合策略审查：职业指令 × 护卫拦截

状态：生产整合候选的独立实际模型完成，规则结果通过；公开发行仍有实机/外部玩家门禁。冻结 P08 的玩法、关卡与资产作为对照；P09 不通过人为提高抽取概率、共享稀有度或数值加码伪造深度。用户要求持续高并行，故保留各独立原型证据并迅速整合有因果证据者，而不是等待主观日历；最终发布仍须通过实机、画面、教程、声音和WebGL2入口门禁。

## 1. 已选择机制和未采用候选

- 铜鸣只 FRONT，初始指令保持 P08 实际最近终点逻辑。潮雾可选 SCREEN（先控未减速敌，余按前线），礁锤可选 CLUSTER（当前溅射可打中更多实际其他活敌，余按前线）。仅备战、免费立即改回；无自动推荐所有专长、无强制切换。高优先特殊目标可能让冲线敌漏掉，UI应直说。HEAVY/CONDUCTIVE 共1,440局独立测试支持不因职业对称而纳入，详见 P09-lab 保留记录。
- 护卫拦截：现有 Shellguard 可替半径1.2内且攻击角色实际射程内的非Boss、非guard友军接一次 Brass/Mist 直接攻击；每守卫1.2s（24 tick）冷却，不改变原HP/角色数量、出生、金币、概率、伤害计算；Hammer直伤/溅射、连锁次级绕过；BOSS/guard不可被护卫。先重定向实际目标再按既有 slow/Focus、连锁、潮雾效果计算，不能生成第二次伤害。显示真实护卫准备/冷却和拦截事件，并预告Hammer绕过；无暗中替换目标。独立 Guard lab 证明有空间反制和无Hammer通关情境，尚需和指令叠加验证。
- 不同时加入被独立模型否定的两项关卡变体，保持 P08 三关六波路径、敌压、随机经济、R等级参数；这些仍可继续独立探索，不把实验当已上线。
- 整合机制不是“自动提高胜率”：指令带来玩家主动选择，护卫带来清晰可学的敌方战术挑战。若二者组合导致玩家被迫抽到Hammer或控制策略普遍失效，保留已证实的可选指令并隔离护卫再改。

|---|---|---|

另运行精确 P08 Front 基线，每个种子/路线风险/布局一对，先验证 A 与 P08 相同资产、波次、状态hash、伤害、币、RNG、有序状态完全同语义。合计120 P08 +240 Guard off +240 Guard on =600实际局。

- `generic`：合成条件仅总拥有>5且有同职业同阶匹配；每波花当前可用航币真实随机抽，排序按高阶、ID稳定，逐个选实际路线采样覆盖最大的合法格，至部署上限。
- `special`：同真实购买与合成；如果随机资产有潮雾和礁锤，先部署最高阶潮雾、随后礁锤，礁锤放位评分额外奖励与潮雾覆盖重叠的路段；若无Hammer而有潮雾/铜鸣则选该对，否则用generic。规则用于评估实际构筑联动而非强制指定彩票。其余角色仍按同一逻辑。两种布阵都不直接注入资产、金币、HP、遗物或选职业抽奖。
- 每次选择明确指令调用实际 `set_order` API；确认金币与 loot RNG 无变化。每波调用真实 `start/step`，统计真实 `guard_intercepts` 且只计 event.tick == 当前tick；每事件检查冷却 ready_tick=tick+24，记录实际拦截有效HP、不重复事件。
- 每波起/末 SHA-256 权威数据快照（角色/储备、敌、遗物、币/HP、随机数、实际射击/死亡/潮雾事件、生成、时间等），不含新增纯表现拦截列表；前10个种子逐tick `var_to_bytes` 流摘要，测试同序列的无事件行为。护卫无实际拦截的对照需起波完整状态、绝对tick一致，不能把前波拦截改变过的初始状态冒充无事件回归。
- 对护卫 on/off 同指令、同初始完整状态，比较漏怪/终局/奖励、有效HP转移、真实反例。对开/关指令，允许指令本身不同，但要求同波资产ID、类型/等级、格位、遗物、HP、金币、loot RNG一致，比较战局。若奖励改变导致后续不同预算，后续分支依然统计策略胜负，但不再称同资产。
- 检查最终获胜中，在所有 guard 出现波均未部署Hammer的自然随机例；目的是反证强制抽取，不是所有无Hammer局必胜。分析两个布局下订单边际 `B−A` 与 `D−C`，以及护卫边际 `C−A` 与 `D−B`；小样本不当做人类胜率或统计显著。

采用判据：A 与 P08 必须完全等价；同初始且无拦截的波不得有任何实际状态偏差；先保持早期可通过性和原随机规则。护卫与指令有真实可读行为，且同资产存在可解释的改善与代价，并有无Hammer可用路径；若D普遍恶化且无法清楚说明何时切回默认或调整站位，则不强制组合。战局代理评估战术可能性，真实新手第一次能读懂预报、准备指令、拦截与恢复，是独立公开门禁而非换算胜率。

## 4. 实际结果（独立 Godot 4.7.2、600整局）

上述完全相同文件SHA均核对。程序成功结束；120个精确 P08 Front 与 guard-off候选默认 Front 的整局记录 **120/120相等**（每波起/末权威hash；其中40个整局含前10种子的逐tickhash）。240个guard-on局全部有真实拦截。对于同订单、完整准备态和绝对tick一致、候选该波无实际拦截的对照，共 **487波**所有结束hash/伤害/击杀/潮雾/奖励/时长一致，其中 **161波**全逐tick摘要也一致，零不匹配。所有600局均完成前两波。这个结论不包含显示帧率、真人体验或纯表现元数据比较。

## 5. 独立结论

**推荐保留已经明确的二项可选指令与护卫机制整合候选，不改随机、R3、收入、HP或其他规则，不强制抽指定克制角色。** 2×2证据显示指令对护卫情境仍有明显策略空间，Guard本身又不引入统一增伤、无事件语义偏移或隐藏彩票强制条件。特殊阵型与默认覆盖都存在正反例，优先解释为何切回Front、如何考虑护卫和风险，不自动推荐“全部开”或“必须有Hammer”。

该推荐同时附条件：实际阅读/操作任务需从无说明入口理解（1）守卫替谁承伤、准备/冷却徽标；（2）SCREEN/CLUSTER的目标与可能漏前排的代价；（3）可以自由移位/取消指令、避开风险、不是固定DPS预测。若guard的攻击转移难被真实玩家观察，先改预报、拦截连线/标志与教程；若机制在实际认知门槛下仍成为随机失控，再隔离/关闭护卫而不牺牲已证实的可选指令。600局及161逐tick摘要不是新手真人A/B，更不能保证外部WebGL2可玩。真人反馈、系统帧率/分辨率及发行最终包仍由生产验收门禁确认。
